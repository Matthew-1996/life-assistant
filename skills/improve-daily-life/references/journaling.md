# 对话式生活日记工作流

仅在用户提供生活记录、要求写日记、回顾日记，或需要从日记提取规划线索时读取。本工作流的目标是让用户用自然对话留下生活，而不是让用户维护一套复杂表格。

## 1. 触发判断

### 明确触发：直接记录

以下任一种表达都视为明确的留存意图：

- 消息以“日记：”“日记记录：”“生活记录：”“记录一下：”等词开头；
- 用户说“写进日记”“帮我记下来”“存到日记”；
- 用户明确要求补记、更正、查看、整理或删除某篇日记。

若消息只有触发词、没有正文，不创建空记录；只请用户继续发送正文。

### 隐式触发：谨慎记录并告知

用户没有说触发词，但消息明显在叙述一段亲身经历，并包含事件与时间、地点、人物、感受或意义等具体细节时，可以视为希望留存。记录后必须明确告诉用户，并提供一句低负担撤回方式，例如“如果你只是想聊聊，说‘不要记刚才那条’即可撤回”。

以下内容默认不自动记录：

- 单纯提问、求建议、假设或计划；
- 复制的文章、新闻、会议材料或他人叙述；
- 编程、工作排障等与生活留存无关的任务；
- 没有明确留存意图的孤立状态，例如“我现在放下手机准备睡觉了”。

边界不清时继续回应当前内容，不要为了建档打断用户；可以在回答末尾非阻塞地问是否要记入日记。

## 2. 入库顺序

1. 先检查即时安全风险。若出现自伤、暴力、急症或其他立即危险信号，先给安全响应，再决定是否归档。
2. 识别发生日期与时间精度。优先使用用户明确给出的日期；用户没有提供具体时刻时，保存 `time=null`、`time_precision=unknown`，不要拿记录时间冒充事件时间。用户只说“大约九点”时可保存 `21:00` 与 `time_precision=approximate`。`recorded_at` 始终另存真实记录时间。
3. 保留用户原话。除了遮蔽不应保存的秘密，不改写、不补全、不把推断混入原文。
4. 生成简短标题和一句摘要。
5. 分栏提取：明确事实、用户明确表达的感受、人物、地点或场景、生活主题、标签、可能影响后续规划的线索。
6. 所有推断都标为“待确认线索”，不得写成人格、关系、健康或价值观结论。
7. 普通新增优先按 `journal/QUICK_CAPTURE.md`，通过非 PTY、`shell=False` 子进程的 stdin 调用项目内 `tools/journal_manager.py add --input -`；不要把含原文的 JSON 留在项目目录、命令参数或 PTY 回显日志。`add` 会原子写入月度 Markdown、机器索引和可读索引。iCloud 本地成功就是归档成功；若私密 Google 表格已连接，随后只刷新轻量索引，失败留待下次写入重试，不回滚或阻塞本地结果。普通新增不运行完整性检查、项目验证、状态刷新或备份。
8. 给一句回执：日期、标题、已保存在 iCloud 项目；仅在 Google 刷新失败时补充一句“展示层待同步”。默认不追加问卷。归档 XLSX 只在用户明确导出、恢复或迁移时重建。

## 3. 存储契约

项目内结构：

```text
journal/
├── README.md
├── PRIVACY.md
├── INDEX.md
├── review-policy.json（试运行与长期整理节奏；长期选择未确认时保持 pending）
├── index.jsonl
├── .operations/（仅在永久删除中断时暂存恢复元数据）
├── entries/YYYY/YYYY-MM.md
└── reviews/YYYY/YYYY-Www.md 或 YYYY-MM.md
```

每条日记至少包含：

- 稳定条目 ID、发生日期、可选发生时刻及其精度，以及独立的记录时间；
- 标题、来源（明确触发或隐式触发）和隐私级别；
- 用户原话；
- 一句话摘要、明确事实、明确感受、人物、地点或场景、生活主题、标签和规划线索；
- 更正或撤回状态。

`INDEX.md` 和私密 Google 表格只保存便于查找的轻量索引，不复制完整原文。网页只介绍功能和使用方式；未经用户针对具体范围的当次明确同意，不展示原始日记或敏感摘要。

## 4. 隐私、更正与删除

- 默认隐私级别为 `local-only`：日记工具只把原文写入当前 iCloud 项目，不发布到网页或外部表格；在用户已确认的私密 Google 展示层中，只同步日期、标题、摘要、人物/场景等轻量索引。它不等于离线或只有一份副本。对话产品保留、iCloud 同步、Google 派生副本、未独立加密 ZIP 和删除边界以 `journal/PRIVACY.md` 为准。
- 密码、访问令牌、完整证件/银行卡信息、恢复码、完整或截断的私钥块和第三方秘密不得落盘；以“敏感信息已省略”代替。遮蔽要支持全角冒号、引号中的空格和分组恢复码，但不把“我们关系的密码是坦诚沟通”这类自然语言比喻删掉。
- 不因为用户曾授权某类健康信息私密发布，就推定其授权发布全部日记。
- 用户更正日记时，用 `journal_manager.py amend --input -` 保留带时间与稳定标识的更正记录，以最新明确陈述为准，不静默改写原文。只更正日期/时间时可只传时间字段；任何内容更正都必须在同一次调用中重新提取并提交完整轻量索引，不能只追加 `note` 后继续沿用旧摘要、人物或事实。日期或时间说错时可以修正轻量索引中的有效时间及精度，同时保留首次值并保持原始月度文件不移动；刷新 Google 轻量索引，并刷新所有被标记失效的共享旧回顾。
- 用户要求“不要再用”或“撤回”时，先解析到具体条目并用 `withdraw` 做逻辑撤回。撤回会隐藏条目但保留原文和机器索引，可用 `restore` 恢复；回执必须明确它不是删除。
- 用户说“不要记刚才那条”时，使用 `journal_manager.py withdraw-latest-implicit` 按 `recorded_at` 原子解析并撤回最近一次仍有效的隐式记录，不按事件日期猜测；再刷新 Google 轻量索引。若该条目已进入旧回顾，工具会把回顾标为需要刷新；刷新完成前不得继续用该回顾做规划或长期记忆。
- 用户明确要求永久删除时，先运行只读 `purge-plan`，展示日期、标题、受影响回顾、可识别 ZIP 和删除范围，再取得当次明确确认。只有先 `withdraw`、`--confirm` 与条目 ID 完全一致、用户知晓旧 ZIP/聊天/iCloud/设备备份可能保留副本后，才运行 `purge --acknowledge-historical-copies`。`purge` 只接受具有匹配 `journal-review` 标记、且在“来源日记”中精确包含目标 ID 的受管回顾；异常引用 fail closed，不删除无关文件。
- 真正删除前，恢复契约冻结目标原文块 SHA-256、索引回顾引用、受管回顾路径和 SHA-256；契约不得含原文、标题、摘要或未知字段。存在 pending purge 时，除同一 ID 的 `purge` 收尾外，其他日记写操作都停止。中断后若原文块、回顾内容/来源、路径集或索引引用漂移，保持操作冻结，不自动扩大删除范围，也不声称完成。当前无自动 replan/abort 命令；先人工核对并恢复原冻结契约，契约无漂移时再用 `purge-plan` 确认 `resume` 并以同样确认安全重跑，完成后再刷新 Google 派生视图。
- `purge` 只证明当前项目副本已删除。若用户要求删除所有历史副本，另行列出可识别 ZIP 及配套校验文件并逐项审批；平台与 iCloud 保留需要用户在相应产品中处理。范围不明确时不得批量删除。

## 5. 回顾节奏

只有存在新增日记时才生成回顾；空白不是失败，也不要求补写。定期回顾先读取 `journal/review-policy.json` 判断本次是否属于已确认节奏，再用 `journal_manager.py review-plan --type weekly|monthly --as-of YYYY-MM-DD` 只读列出已经闭合、缺失或来源集合发生变化的周期。计划只返回日期、受管路径、原因、完整 active 条目 ID 集合和不含原文的 `source_set_etag`。再按计划中的精确 ID 读取来源块，由助手基于明确内容生成结构化草案，并把同一次计划返回的 `source_set_etag` 原样传给 `journal_manager.py review`。工具在锁内重读该周期全部 active 来源并精确核对集合与指纹；若计划后有补记、撤回或更正，本次不写入，重新运行计划后再尝试。成功后再次刷新 Google 表格，使相关记录显示为“已纳入周回顾”或“已纳入月回顾”；外部刷新失败只标记展示层待同步。

### 每周轻回顾

- 本周实际发生的三件事以内；
- 哪些活动、环境或关系带来补充与消耗；
- 反复出现的人、地点、活动或摩擦；
- 仍未结束的线索；
- 一个对下周规划有用的启示。

周回顾完整覆盖同一 ISO 自然周的周一至周日；同一周重新生成时刷新原文件，不产生相互冲突的副本。跨年周按 ISO 周所属年份命名。

定时周回顾在下一个周一处理刚结束的自然周，不在周日白天提前封账；这样周日下午或晚间新增内容也能进入完整周期。后来补记到旧周期的日记会让 `review-plan` 再次列出该周并安全刷新。长期采用每周、每月、仅按需还是暂停，仍按用户明确选择执行；未选择时不默认新增长期提醒。用户明确选择后，先用 `journal_review_policy.py show` 获取当前节奏，再用 `set --expect-current <刚读取值>` 保存决定日期与试运行结束后的生效日期；工具陈旧冲突时重新读取，不覆盖较新的选择。

这里的日记周回顾是从有效日记生成的叙事性派生材料，不等于用户对主动周复盘问题的明确回答。后者保存在 `records/weekly-reviews.jsonl`，只能由用户回答生成，不得从日记回顾反向填充；两者可通过 ISO 周关联，但删除或撤回一边不会自动删除另一边。

### 每月生活回顾

- 值得记住的生活片段和变化；
- 反复出现的偏好、价值或需要，但标为候选认识；
- 用户可能想增加、减少、继续或停止的事；
- 需要用户确认后才能进入 `USER.md`、`MEMORY.md` 或 `GOALS.md` 的摘要。

月回顾完整覆盖同一自然月的首日至末日；`candidate_memories` 必须以“待用户确认”呈现。用户没有确认时，只保留在回顾中，不升级为长期事实或目标。

定时月回顾在次月 1 日或之后处理刚结束的完整自然月；不会在月末尚未结束时提前生成。

### 候选认识确认

回顾成功且需要向用户展示长期认识或规划线索时，通过非 PTY stdin 向 `python3 tools/journal_insights.py plan --input -` 传入空 JSON 对象。每次最多展示 3 个候选；只询问 accept/reject，不把沉默当作接受。已决策候选不重复出现，回顾来源变化时旧候选变为 `superseded`。

用户明确接受或拒绝后，使用刚展示的 `candidate_id`、revision 和 etag，通过 stdin 运行 `journal_insights.py decide --input -`。工具只记录决策；accept 进入 `awaiting_proposal`，不写长期文件。随后用 `propose --input -` 保存白名单目标文件与精确拟写文字，用 `apply-plan --input -` 只读取回并向用户展示；`apply-plan` 是唯一允许返回精确提案的命令，不能从台账、旧对话或记忆猜回。只有用户对这个精确变更再次确认后才真正编辑 `USER.md`、`MEMORY.md` 或 `GOALS.md`；验证目标当前字节已包含精确提案后，再用 `mark-applied --input -` 标记。`mark-applied` 不会代替编辑；提案可用最新 revision/etag 修订，回顾来源漂移时旧提案自动转为 `superseded`。

`propose` 的 stdin JSON 是 `candidate_id`、`target_file`、`proposal_text`、`expect_revision`、`expect_candidate_etag`；`apply-plan` 不含文字，只传候选 ID 与 revision/etag；`mark-applied` 再加 `expect_proposal_sha256`。`list/status` 及 inspector 只用于安全状态检查，不输出摘要、目标、提案、回顾路径/哈希或来源日记 ID。

自动周一整理不因为产生候选就额外打扰用户；只在用户当次请求回顾、月回顾或阶段复盘的合适节点展示。日记是生活资料，候选也不是打卡指标。

日记是生活资料，不是打卡指标。不要计算连续天数、给生活评分、诊断人格或自动改变目标排序。

## 6. 回执模板

明确触发：

> 已记入 2026-08-01 的日记：《标题》。原文和整理结果已归档到你的 iCloud 项目；日记工具不会自动发布它们。

隐式触发：

> 我把这段作为生活日记保存了：《标题》。如果你只是想聊聊，说“不要记刚才那条”即可撤回。

仅触发词无正文：

> 可以，直接把想记录的内容发给我就好；不用整理格式。
