# 生活日记隐私与删除边界

这份说明定义日记数据实际经过哪里，以及“更正、撤回、恢复、永久删除”分别意味着什么。目标是避免把 `local-only` 误解成“只在一台设备、从未经过云服务”。

## `local-only` 的准确含义

`journal_manager.py` 中的 `local-only` 表示：工具只把日记原文与结构化归档写入当前 iCloud 项目，不主动把原文发布到 OpenAI Sites、Google 表格、消息连接器或其他外部服务。

它不表示离线或只有一份副本：

- 用户通过当前对话发送的原始内容，可能按所用对话产品与账户的保留设置保存；
- `journal/entries/` 位于 iCloud 项目，会由 iCloud 同步到获准访问该账户的设备；
- `tools/create_backup.py` 创建的是没有独立日记密码的标准 ZIP；存在真实日记时，ZIP 会包含原文和回顾并明确打印提示；
- `journal/insight-decisions.jsonl` 如已创建，ZIP 也会包含候选的二次去敏摘要、决策状态和溯源哈希；已进入 `proposed/applied` 的历史还会包含拟写入长期文件的精确文字、目标和哈希。它不含日记原文，但仍是敏感的个人生活派生数据；
- iCloud 版本历史、设备备份和已经生成的旧 ZIP 不受日记工具直接控制。

用户已经确认的私密 Google 表格展示层只接收有效日记的日期、标题、摘要、人物/场景、主题与整理状态，不接收 `raw`；它是 iCloud 源数据的只读派生副本，不反向写入项目。Google 与归档 XLSX 都只在用户明确要求时按需刷新。移动网页已归档且不再部署；没有针对具体范围的当次授权时，不向任何外部服务发布原文或摘要。

候选认识工具只从受管回顾的固定章节提取候选，不读取日记原文。它会二次遮蔽高置信秘密、联系方式、长号码和日记稳定 ID；对用户展示的 `plan` 仍可能含个人生活摘要，不应发布到网页或外部连接器。“接受”只进入 `awaiting_proposal`；提案只能由只读 `apply-plan` 取回并展示，精确变更再次确认后才真正编辑长期文件，`mark-applied` 仅核验已写入的字节。`list/status` 不输出内容，不等于台账文件本身不敏感。

Google 表格日常同步不生成本地预览图片。只有明确重建归档 XLSX 时才会渲染结构与公式检查图；人工指定目录留下的历史 PNG 可能包含轻量日记索引、睡眠或情绪派生视图，应按敏感文件管理，清理前仍需确认确切范围。

## 四种数据动作

| 动作 | 当前项目中的效果 | 原文是否仍保留 | 对旧回顾的处理 |
|---|---|---:|---|
| 更正 `amend` | 追加带时间与稳定标识的更正记录；时间更正保留首次值，内容更正必须完整重建轻量索引，不覆盖或移动原文 | 是 | 整份共享回顾对所有来源标记失效，刷新前不得用于规划 |
| 撤回 `withdraw` | 从可读索引、Google 表格同步来源和未来回顾中隐藏；机器索引保留撤回状态 | 是 | 标记失效 |
| 恢复 `restore` | 将尚未永久删除的撤回条目恢复为有效 | 是 | 旧回顾仍需重新生成，不自动复用 |
| 永久删除 `purge` | 删除当前项目中的条目块、机器索引记录，并删除可能含衍生内容的整份受影响回顾 | 否，仅限当前项目 | 整份删除；其他来源需重新生成回顾 |

同一月的多篇日记共享一个 Markdown 文件，但撤回或恢复标记按稳定 ID 限定在目标条目块内；机器索引使用严格字段白名单，异常字段不会通过 `list` 原样输出。含原文的新增、更正和回顾输入应走非 PTY stdin；PTY 未关闭回显时，终端日志可能形成额外副本。

永久删除前先用只读的 `purge-plan` 展示当前状态、受影响回顾与可识别 ZIP；该预览不输出原文。真正删除必须满足三项保护：先 `withdraw`、`--confirm` 与条目 ID 完全一致、显式使用 `--acknowledge-historical-copies`。索引中的受影响回顾路径不被盲目信任：每份文件必须具有唯一、匹配实际路径的 `journal-review` 标记，且在受管的“来源日记”清单中精确包含目标 ID，否则 fail closed 且不删除该文件。

删除开始前，工具会在 `journal/.operations/` 写入 schema v2 恢复契约。它的顶层字段固定为 schema 版本、操作类型、条目 ID、来源路径、目标原文块 SHA-256、冻结的索引回顾引用、受管回顾路径与 SHA-256，以及带时区的操作时间；不保存标题、摘要、原文或其他未知字段。原文块、回顾、可读索引和机器索引收敛完成后才删除该契约。

契约存在时，除同一条目的 `purge` 收尾外，其他日记写操作都被阻止；只读的 `list` 和 `purge-plan` 仍可使用。中断后恢复会重新校验原文块、每份回顾的哈希、精确来源、路径集和索引引用，不把新发现的路径自动并入删除范围。契约未漂移时，状态检查将其显示为待处理，`purge-plan` 返回 `resume`，用相同确认重跑可幂等完成。如果手工编辑、iCloud 并发或其他异常使契约漂移，操作保持冻结，不会自动 replan、abort 或扩大删除；需先人工核对并恢复原冻结契约。它只证明当前项目副本已删除，不能证明聊天历史、iCloud/设备版本或旧 ZIP 中的副本已经消失。

如果用户要求“所有历史副本也删除”，助手必须先列出可识别的 ZIP 及其 `.zip.sha256`、`.files.sha256` 配套文件，并就每个范围重新取得明确批准；对话平台和 iCloud 的保留或删除需要用户通过相应产品设置处理。不得把当前项目的 `purge` 回执表述为全局彻底删除。

当前条目 `purge` 会删除受影响的回顾，但已生成的 `insight-decisions.jsonl` 是独立的确认台账，现阶段不随条目删除命令自动清理。回顾消失后，再运行 `journal_insights.py plan` 会将对应候选标为 `superseded`，但历史摘要、精确提案与应用状态仍可能保留用于决策审计。如用户要求删除这一派生台账，必须把它作为单独当前项目范围识别并再次确认；未实现精确工具前不手工改写或声称已删除。

## 低痕迹输入

助手调用 `add`、`amend` 或 `review` 时优先使用标准输入：

```bash
python3 tools/journal_manager.py add --input -
python3 tools/journal_manager.py amend --input -
python3 tools/journal_manager.py review --input -
```

不要把包含原文的 JSON 放进项目目录、命令参数或终端历史。必须使用临时文件时，只放在系统临时目录，成功或失败后都立即清理；临时文件不进入项目备份。

所有日记命令都使用项目内锁覆盖完整的读改写区间。并发请求会串行处理；若等待超时，本次命令明确失败且不应被回执为已记录。锁文件不含日记内容，也不进入 ZIP。

备份先固定本次要打包的精确文件集合与字节，并直接在内存快照上核对日记索引—原文双向关系；ZIP 和 manifest 都只由这组字节生成。发布三件套前再次逐文件核对路径集合、身份、模式、内容和哈希；任何新增、删除、替换或内容变化都拒绝发布，错误信息不复述日记内容。

## 目前没有自动启用的保护

- ZIP 没有单独的日记密码或端到端加密密钥；是否增加独立加密以及密钥如何保管，需要用户单独决定。
- 工具不会自动删除旧 ZIP、聊天历史、iCloud 版本或设备备份。
- 工具不会因为多篇日记出现相似内容，就自动把推断写入长期记忆或改变目标。

这些限制是为了避免在用户不知情时制造无法恢复的删除或密钥丢失风险。
