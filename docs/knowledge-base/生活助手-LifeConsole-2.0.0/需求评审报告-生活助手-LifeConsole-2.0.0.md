| 需求合理性 | **高** | 直接解决 1.0.0 的本机部署丢失、换机成本高、双向同步复杂、审计缺失、健康明细管理难 5 个痛点 |

| 隐私可行性 | **高** | 字段级加密 + 最小明文索引 + Owner-only 会话 + 审计链，隐私控制优于 1.0.0；关键风险为 KEK 管理与恢复包，PRD 已有明确约束 |

## 4. 成本、风险与取舍

### 成本

- **开发成本**：
  - 阶段 A（合成联调）≈ 2 个工作块：Worker API + D1 Schema + 加密 + 前端 API 接入
  - 阶段 B/C（预览+密钥+部署）≈ 1 个工作块：Sites 部署 + 密钥 + Owner-only 校验
  - 阶段 D/E/F（真实迁移+切源）≈ 1 个工作块：迁移工具 + 系统页状态流 + 切源验证
- **运维成本**：季度密钥轮换 + 冷备同步监控 + 每年一次恢复包演练
- **经济成本**：Cloudflare Workers + D1 + R2 在单用户量级几乎为免费套餐覆盖；风险在套餐配额变更

### 风险

| 风险 | 概率 | 影响 | 缓解策略 |
|---|---|---|---|
| Cloudflare 区域故障，站点不可访问 | 低 | 高（无法写入） | 保留 iCloud 冷备最近 7 天写入副本；降级：在本地用同步代理直接写 iCloud，故障恢复后再回灌 D1 |
| KEK 丢失 + 恢复包也丢失 | 极低 | 极高（密文不可恢复） | 强制 3 份恢复包存储位置（本地 + 外置 USB + 云密码管理器）+ 每季度恢复演练 |
| 迁移中途断网/浏览器崩溃 | 低 | 中 | 迁移状态机持久化；每个阶段可从断点继续；VALIDATING 阶段失败可直接重来 |
| 7 天回滚窗口后发现迁移数据不一致 | 极低 | 高 | 窗口结束前再次执行全量（ID × revision × 哈希）校验并展示报告；PO 确认后才关闭窗口 |
| 前端冲突 UI 不清导致用户误操作 | 中 | 中 | 设计阶段出 409 交互稿；合成 E2E 强制 3 次冲突演练 |

### 取舍

- **不直接合并 1.1.0 Draft PR #35**：其「只读快照」定位与 2.0.0 矛盾，改为人工提炼构建脚本与前端骨架。
- **D1 而非 Cloudflare KV**：生活数据是关系型（日记 revision、健康片段、多对一关系），D1 更合适，KV 不作为主存。
- **字段级加密而非整库加密**：允许服务端按明文字段做索引与趋势查询，同时保护原文隐私。
- **AES-GCM 而非 ChaCha20-Poly1305**：Web Crypto API 原生支持更好，Worker 端兼容性优先。
