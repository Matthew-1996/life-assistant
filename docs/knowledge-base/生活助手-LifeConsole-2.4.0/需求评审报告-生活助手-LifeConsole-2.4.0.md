# 需求评审报告：Life Console 2.4.0

## 1. 结论

需求成立，必须作为新版本治理，不能用前端文案或单个 Prompt 快速修补。根因同时存在于输入整理、Repository 字段映射和前端渲染。

## 2. 方案比较

| 方案 | 一致性 | 质量 | 可靠性 | 结论 |
|---|---|---|---|---|
| 各入口复制同一段 Prompt | 中 | 高 | 中 | 仍会漂移，不采用 |
| 全部使用确定性首句/关键词规则 | 高 | 低 | 高 | 无法达到 Agent 整理质量，不采用 |
| 统一契约 + Agent 主处理 + 服务端模型兜底 | 高 | 高 | 高 | 推荐，需治理模型差异与数据处理边界 |
| 所有入口固定只用一个外部模型 | 最高 | 高 | 中 | 输出更一致，但违背 Agent 优先且扩大私人数据外发 |

## 3. 主要风险

1. “统一”不能被误解为两个模型逐字输出相同；可验收的是字段、事实边界、证据类型、空值和渲染一致。
2. DeepSeek 会收到被兜底处理的日记原文及最小必要人物字典，属于新的第三方数据处理。
3. JSON Output 只保证 JSON 可解析，不保证满足业务 Schema 或事实正确，必须本地校验。
4. Agent 与兜底模型升级可能改变结果，必须锁定模型名、Prompt 版本和黄金案例。
5. 个人档案不能整份发送；只允许逐项获批的最小人物别名投影。

## 4. Gate 2 待确认

- Q1：同意混合处理架构，而非追求跨模型逐字相同。
- Q2：同意网页等非 Agent 入口把当篇原文发送到 DeepSeek 官方 API。
- Q3：同意兜底首选 `deepseek-v4-flash` 非思考模式；质量 POC 不达标时再评审 `deepseek-v4-pro`，不自动换模。
- Q4：同意只把逐项确认的人物别名与关系投影到 Supabase；真实条目仍需逐项授权初始化。
- Q5：同意 Vercel 服务端函数持有 DeepSeek Secret，浏览器、Git、日志和 Supabase 不保存密钥。
- Q6：同意先做纯合成 POC 和候选部署；本 Gate 不包含真实日记处理、历史批量整理、Production、资源删除或 PR 合并。
