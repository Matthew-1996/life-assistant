## 1. 产品定位

生活助手是一套以降低认知负担、改善现实生活质量为目标的长期 Agent 系统。它通过对话完成记录、规划、回顾和确认，以 iCloud 私有项目作为个人数据真相源，并用 Life Console 提供 Mac 本机的可视化查看与低成本输入入口。

Life Console 是生活助手的 Mac-first 本地客户端，不是独立的个人数据真相源。它读取经过白名单约束的投影，并通过本机 Life Hub 调用既有原子工具写入 iCloud。

## 2. 用户问题

历史需求集中解决以下问题：

1. 生活信息分散在对话、文档和临时记忆中，长期难以回顾和迁移。
2. 手工维护大型表格和文档成本高，容易中断记录。
3. 多个生活目标会互相叠加，缺少清楚的主次、阶段和可暂停机制。
4. 睡眠、精力、情绪、生活体验和日常行动需要低压力跟踪，但设备数据不能替代主观感受。
5. Agent 主动维护容易越权：自动推断、重复副本、错误日期、未确认的外部动作或产品改动都会降低信任。
6. 工作电脑、换机和多 Agent 协作要求项目具备可迁移、可审计、可恢复且不泄露个人数据的工程基础。
7. 只有对话入口时，回顾和系统状态不够直观；只有表单入口时，记录负担又过高。

## 3. 产品目标

### 3.1 核心目标

- 让用户可以用一句自然语言完成日记、状态或生活计划相关输入。
- 把目标、记录、回顾和确认分层保存，保持可纠正、可撤回、可迁移和可审计。
- 用动态优先级和阶段复盘减少目标叠加，不把生活管理变成新的压力来源。
- 在 Mac 本机提供清晰、安静、可信的查看与兜底输入界面。
- 让 Agent 和多个开发 Agent 能够基于稳定规则、文档与测试长期维护产品。

### 3.2 成功标准

- 本地真相源写入成功后即可确认，不受外部展示失败影响。
- 同一请求幂等，不产生重复日记或重复状态。
- 日期、未知、跳过、最低版和完成在数据与界面中保持不同语义。
- 删除、更正、覆盖、发布、共享和真实数据迁移都有清楚范围与确认门禁。
- Life Console 只绑定本机回环地址，个人数据不进入 Git、合成测试、URL、日志或浏览器持久化。
- 新 Agent 能从项目规则、知识库、PMO 和 Git 工作流继续维护，不依赖旧聊天或单台机器缓存。

## 4. 目标用户与使用场景

### 4.1 目标用户

需要低认知负担生活协助、愿意通过对话留下少量信息、重视隐私与可控性的个人用户。当前 1.0.0 只面向单用户、Mac 本机和私有 iCloud 工作区。

### 4.2 核心场景

- 通过对话快速记录日记、感受、生活事件和计划线索。
- 回答短回访，记录当天主观状态和行动锚点。
- 在完整自然周或阶段结束后复盘并调整目标。
- 用 Apple Health 最小客观摘要辅助核对睡眠和活动，不替代主观评分。
- 在 Life Console 查看今天、记录、进展和系统状态，并用简洁表单兜底。
- 在删除、覆盖、外部发布或调整长期目标前查看精确影响并确认。
- 换机或多 Agent 协作时，通过项目内规则、工具、知识库和测试恢复工作。

## 5. 产品原则

1. **降低认知负担**：首屏和回访只呈现当前必要信息，不制造打卡压力。
2. **对话优先、表单兜底**：自然语言是主要入口，常用字段表单保持简洁，高级字段按需展开。
3. **用户控制**：Agent 可以生成草稿和建议，产品决定、重大取舍和高影响动作由用户确认。
4. **真相源分层**：iCloud 私有项目保存事实；网页、表格和 Console 都是派生视图或受控入口。
5. **未知保持未知**：不从缺失、设备数据、日记或均值推断用户未提供的主观结论。
6. **隐私最小化**：GitHub 只保存通用代码和合成示例；个人数据不进入 Git。
7. **可恢复与可审计**：写入、变更、撤回、删除、迁移和发布都有稳定标识、版本或证据。

## 6. 功能需求

### FR-01 用户、记忆与目标分层

- 稳定偏好、长期事实和目标分别维护，不把一次性经历自动升级为长期认识。
- 目标支持当前重点、辅助、候选、暂停和完成状态；新增目标需要重新排序，不默认叠加。
- 长期认识和目标变更必须展示精确提案并由用户确认。

### FR-02 对话式日记

- 支持显式触发和受限的隐式归档；普通问题、转发材料和孤立状态不自动记日记。
- 原文按月保存在私有 iCloud 项目；机器索引只保存严格白名单字段。
- 支持新增、更正留痕、逻辑撤回、恢复、永久删除计划和周/月回顾。
- 不知道具体事件时刻时保持未知，不使用记录时间制造假精度。

### FR-03 每日状态、自然周和阶段复盘

- 每日主观评分统一归明确标注的日期；睡眠质量评价今早结束的一晚，其他评分评价回访时当前状态。
- 自然周复盘固定覆盖周一至周日；阶段复盘固定写回发起日。
- 每日、周、阶段和日记台账互相独立，除非用户明确要求，不跨台账自动复制。
- 所有台账支持幂等更新、revision/etag 冲突保护和精确删除预览。

### FR-04 Apple Health 最小客观辅助

- 允许读取和归档用户已授权的最小客观摘要，用于睡眠时间校准和趋势辅助。
- 设备数据不填写睡眠质量、精力、情绪、生活实感或行动完成状态。
- 设备睡眠结束只表示最终醒来，不覆盖用户离床时间。
- 健康数据只保存在 iCloud 私有台账，不进入 Google、网页、连接器或 Git。

### FR-05 Life Console 本机工作台

- 提供工作台、记录、进展、系统四个核心目的地。
- 展示今天必要信息、确认后的辅助项目、生活锚点、近期记录、自然周进展和系统边界。
- 使用对话式记录主入口、运动/锚点快捷记录和简洁表单兜底。
- 只连接 `127.0.0.1` 的 Life Hub；浏览器不成为个人数据真相源。

### FR-06 Life Hub 受控读写

- 只返回白名单字段；读操作使用短时会话，写操作要求同端口 Origin 与 CSRF。
- 日记和每日状态写入复用既有原子工具，不新增平行数据源。
- 写入返回幂等收据；冲突、部分刷新和失败不得伪装为成功。
- 删除必须先计划、再精确确认；不夸大对聊天、旧备份或设备历史的删除范围。

### FR-07 自动整理与语义增强

- 日记可按策略生成轻量结构化摘要和待确认增强结果。
- 语义增强不能覆盖原文或直接升级为长期记忆；失败保持原始记录可用。
- 外部模型凭据只使用机器安全存储，不进入项目、日志或前端。

### FR-08 展示层与同步

- iCloud 始终是唯一真相源。
- 本地 Numbers 兼容工作簿、Google 表格和移动端网页只做派生展示；生命周期和刷新节奏受显式配置控制。
- 外部展示失败不回滚本地记录；公开发布或共享必须获得当次明确确认。
- 1.0.0 的主展示方向是 Mac Life Console，移动端保持后续决策。

### FR-09 主动回访与提醒

- 回访使用明确日期、少量问题、可复制模板和低打扰语气。
- 自动化规格必须保存在项目内，运行实例属于机器本地状态，可按规格重建。
- 未回答、跳过和沉默不能自动改变目标、节奏或长期记忆。

### FR-10 隐私、迁移与恢复

- 个人资料、记忆、目标、日记、状态、健康、绑定、导出和备份不进入 GitHub。
- 备份、恢复、完整性检查和便携性验证不依赖旧机器绝对路径或缓存。
- Git 隐私检查同时覆盖当前索引和新增历史，不能只看当前文件树。

### FR-11 项目治理与多 Agent 协作

- 开发工作遵循最高优先级项目开发规范和 `GIT_WORKFLOW.md`。
- 每个产品版本有 PRD、PMO 状态和按阶段生成的设计、技术、测试、验收材料。
- 用户确认门禁不能被测试、提交或 Agent 推断替代。
- 并行 Agent 使用独立 worktree、独立分支和 Draft PR，不覆盖他人修改。

## 7. 非功能需求

### 7.1 安全与隐私

- 默认本地、最小权限、最小数据、合成测试、去敏日志。
- 拒绝非回环绑定、未知命令、未授权写入和高置信凭据入库。
- 公开发布、真实数据迁移、删除和外部共享都采用显式确认。

### 7.2 正确性与一致性

- 写入幂等、原子替换、稳定 ID、revision/etag 和源漂移检测。
- 派生视图不反向覆盖真相源；未知字段不从旧视图补回。
- 测试覆盖正常、失败、冲突、并发、隐私和恢复路径。

### 7.3 可维护性

- Python 核心工具优先使用标准库；前后端契约集中定义并可生成验证。
- UI 先维护设计系统、交互基准与长期 UI/UE 规范，再同步实现。
- 每次迭代复核模块、存储、接口、迁移、回滚和重构必要性。

### 7.4 可迁移性

- 项目规则、文档、工具和测试保存在 iCloud 工作区；运行依赖可在新机器重建。
- 个人实例不能仅靠 GitHub 克隆恢复；GitHub 只提供通用工程基座。

## 8. 当前信息架构

- **生活助手 Agent 层**：用户约束、记忆、目标、Prompt、Skill、回访与规划规则。
- **私有数据层**：iCloud 中的日记、每日/周/阶段台账、健康摘要和派生收据。
- **原子工具层**：新增、更新、撤回、恢复、删除、回顾、同步、验证和备份工具。
- **Life Hub 层**：localhost 白名单读模型、受控命令适配、会话/Origin/CSRF、安全日志。
- **Life Console 层**：React Mac 工作台、记录、进展和系统界面。
- **派生展示层**：按需工作簿、Google 表格和只读移动端站点。
- **工程治理层**：开发规范、知识库、Git 工作流、隐私扫描、CI 与测试。

## 10. 1.0.0 非目标

- 不开放公网、局域网或多用户个人数据 API。
- 不把移动端原生 App、PWA 或公开站点作为 1.0.0 完成条件。
- 不新建云数据库，也不把 Google 表格、浏览器存储或 Todo 工具变成真相源。
- 不根据健康数据做医学判断，不根据缺失记录做人格或能力结论。
- 不自动确定长期职业、健身或其他生活目标优先级。
- 不把所有既有研究、设计和审计复制到知识库目录；使用可验证链接维持单一来源。

## 11. 验收标准

1. 对话式日记和每日状态可通过原子工具与 Life Console 保存，并能读回相同事实。
2. 重复请求不产生重复记录；revision 冲突不会静默覆盖。
3. 撤回、恢复和两步删除能准确说明作用范围并保留必要审计。
4. Life Hub 仅监听回环地址，个人内容不进入 URL、日志、测试夹具或 Git。
5. 设计实现遵循当前 `docs/design/` 基准；偏离有记录和评审。
6. 全仓隐私扫描、相关 Python/Node 测试、前端构建和项目验证通过。
7. 项目知识库能从本 PRD、PMO 和证据链接追溯当前状态，不把开放 PR 写成已完成。
8. 涉及需求、设计、重大技术偏离、验收和上线的用户确认有明确记录。

## 12. 风险与技术债

- 历史需求先开发后补 PRD，本文件只能建立基线，不能恢复所有当时讨论细节。
- GitHub 通用仓库与 iCloud 私有实例分离，完整项目验证需在私有工作区运行；CI 只能覆盖不依赖私有数据的测试。
- 设计治理和实现仍可能随新需求漂移，需要每次迭代先评审设计与技术方案。
- 当前 Code Wiki 仍是开放 Draft PR；在合入前不能作为稳定技术知识入口。
- 移动端、外部展示和自动化属于独立生命周期，不能由代码存在推断为已启用或已发布。

## 13. PO 确认结果

PO 于 2026-08-10 在当前协作任务中明确确认以下五项，并授权将 PR #28 转为可评审状态后合并：

1. “生活助手”为产品，“Life Console”为 Mac 本机客户端，本历史整合稿定为 `1.0.0` 产品基线。
2. 第 3–7 节的产品目标、原则、功能范围和非功能要求作为后续开发的需求判断标准。
3. 第 9 节的历史状态口径生效：已合并且有验收证据才算完成；开放 PR 和未提交工作树不算完成。
4. 第 10 节非目标生效：移动端、公网访问、新云数据库和自动确定生活目标暂不进入 1.0.0。
5. 后续改变产品行为、信息架构、数据边界或验收标准的需求先走需求评审门禁；符合全部条件的纯维护可走有理由记录的快速通道。

确认范围只覆盖上述 1.0.0 历史基线与治理口径，不自动批准新的产品功能、设计变更、真实数据迁移、外部发布或删除动作。
