# 产品需求文档 - 生活助手 - Life Console - 2.2.0

> 版本：draft.1
> 状态：Gate 1 / Gate 2 已确认 / 阶段 A 通用实现进行中
> PO 输入：确认 2.2.0 立项，先完成 Vercel + Supabase 的产品、需求、设计、技术和测试方案评审
> 当前授权边界：仅文档与评审；不创建资源、不使用真实数据、不部署、不切源、不删除资源

## 1. 背景与问题

Life Console 2.1.0 已形成可在移动端访问的 Vercel 合成预览，并完成“网站只保留 iCloud 最新备份、恢复通过 Agent 对话完成”的界面减法。下一步需要让当前四页工作台具备安全、可维护的在线登录与数据读写能力。

此前 Sites + D1 路线在浏览器访问、回环联调和恢复包复杂度上形成持续阻塞。2.2.0 重新立项，以现有 Vercel 前端为唯一界面，以 Supabase Auth + Postgres 为候选后端，先完成方案评审，再决定是否实现。

## 2. 产品定位

Life Console 是用户本人使用的在线生活工作台：聚合今日状态、目标进展、日记与回访记录，并提供清晰的 iCloud 最新备份状态。首版是单用户产品，不提供公开内容、分享、社交或多人协作。

## 3. 用户价值

1. 在手机和电脑上使用同一个入口查看、记录和回顾生活，而不依赖工作电脑本地服务。
2. 通过登录、数据库行级权限和最小化接口降低个人数据被越权访问的风险。
3. 保留 iCloud 最新备份与 Agent 恢复路径，避免云平台成为唯一不可迁移的数据孤岛。
4. 复用当前已验收界面，减少重复建设和长期维护成本。

## 4. 目标与成功标准

### 4.1 目标

- 建立 Vercel 前端与 Supabase Auth/Postgres 的可评审长期架构。
- 定义单用户登录、数据读写、修订、幂等、删除保护和备份的产品行为。
- 定义从 iCloud 私人真相源到云端的未来迁移门禁，但本轮不迁移。
- 保持 Life Console 四页信息架构与 2.1.0 已验收视觉基线。

### 4.2 后续实现成功标准

| 编号 | 标准 |
|---|---|
| S1 | 未登录访问只能看到登录入口，不能读取个人数据 |
| S2 | Owner 能完成登录、退出和会话恢复；非 Owner 不能读取或写入任何记录 |
| S3 | 日记、每日状态、目标和复盘按版本化契约完成合成 CRUD，冲突不静默覆盖 |
| S4 | 所有暴露表启用 RLS，并通过 Owner、非 Owner、未登录三类权限测试 |
| S5 | 线上失败不会把未保存操作误报为成功，重试不会重复写入 |
| S6 | iCloud 最新备份保持单一入口，备份格式可用合成数据完成导出、校验和恢复演练 |
| S7 | 真实数据上线前完成隐私、安全、迁移、回滚和 PO 验收门禁 |

## 5. 功能范围

### 5.1 纳入方案

- Supabase Email OTP 或 Magic Link 登录，默认禁止未知邮箱自动注册。
- 今日、进展、记录、系统四页从合成数据切换到受权限保护的数据接口。
- 日记、每日状态、目标、周复盘、阶段复盘的读写与修订。
- Apple Health 只定义未来导入后的数据模型和权限，不在浏览器直接连接健康数据。
- 幂等写入、乐观并发、软删除/删除计划和最小审计回执。
- iCloud 最新备份的导出格式、状态和 Agent 恢复说明。
- Vercel Preview、Supabase 本地/测试、未来 Production 三环境隔离。

### 5.2 不纳入当前版本首轮

- 多用户协作、分享、公开页面、社区或社交能力。
- 实时订阅、GraphQL、向量检索、AI 自动总结和文件存储。
- 浏览器直接读取 iCloud、Apple Health 或本机任意路径。
- 在线一键恢复、恢复包口令、复杂密钥托管或用户可见迁移中心。
- 旧 Sites/D1/R2/Secret 的删除或迁移。
- 本轮创建 Supabase 项目、部署、使用真实个人数据或切换真相源。

## 6. 关键产品规则

1. 真实迁移前，iCloud 仍是唯一真相源；云端只允许合成验证。
2. 用户未提供的主观字段保持未知，不由设备或旧记录推断。
3. 日记、状态、目标、复盘和健康数据保持分层，不因存入同一数据库而合并语义。
4. 写入必须显示明确的保存中、成功、冲突或失败状态；失败时保留用户输入。
5. 删除先进入可撤销计划，永久删除需独立 PO 门禁和明确确认。
6. 系统页只展示用户需要理解的登录、同步与最新备份状态，不展示项目 ID、密钥、策略名或底层资源标识。

## 7. 待 PO 确认的产品决策

| 编号 | 决策 | Agent 建议 |
|---|---|---|
| D1 | 首版登录方式 | Email OTP；移动端无需跳转链接，且 `shouldCreateUser=false` |
| D2 | 单用户与未来扩展 | 产品首版单用户，数据模型仍按 `user_id` 隔离，避免日后重构 |
| D3 | 敏感字段加密 | 先完成威胁模型；真实日记/健康数据上线前必须在“仅 RLS”与“应用层字段加密”间再次确认 |
| D4 | 写接口形态 | 普通 CRUD 走 Supabase Data API + RLS；高权限批处理/备份才使用受 JWT 保护的 Edge Function |
| D5 | 备份格式 | 继续版本化 `life-console-backup`，用合成数据验证与 2.1.0 Agent 恢复路径兼容 |
| D6 | Supabase 区域与套餐 | 创建项目前由 PO 根据网络、数据驻留和成本单独选择并确认 |
| D7 | 旧 Sites 路线 | 2.2 实现期停止投入，仅保留历史证据；任何云资源删除另行授权 |
| D8 | 上线路径 | 本地合成 → 独立测试资源 → Vercel Preview → PO 验收 → 正式发布 → 真实迁移，逐门禁推进 |
