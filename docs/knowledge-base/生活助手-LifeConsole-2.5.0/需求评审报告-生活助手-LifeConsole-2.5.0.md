# 需求评审报告：Life Console 2.5.0

## 1. 结论

需求成立，涉及信息架构、Owner 数据模型、数据库 RPC、备份版本、Vercel 内容服务与自动化，必须按正式版本治理。Gate 1 范围与总体架构方向已确认；当前进入正式视觉、设计和技术评审。

## 2. 已确认决策

| 议题 | 决策 |
|---|---|
| 版本方式 | 一个 2.5.0，按可验收阶段推进 |
| Todo DDL | 不自动延后；逾期只派生展示 |
| 日记删除 | 软删除 + 恢复；不提供永久删除 |
| 寄语频率 | 每周一生成，工作台每日展示 |
| 寄语输入 | 活跃目标 + 未完成 P0/P1 Todo + 最近周复盘 |
| 新闻数据 | GDELT 发现、可信域名过滤、DeepSeek 公开摘要、Runtime Cache |
| 趋势分析 | 确定性比较两个 7 天窗口，不调用模型，不作诊断 |
| 私人真相源 | Owner-scoped Supabase；新闻缓存不是私人真相源 |

## 3. 对私人 PRD 的澄清

1. “长周期 Todo 自动根据 DDL 延后”被替换为“DDL 不自动变化，逾期派生”，避免系统未经用户同意重写承诺时间。
2. “每日寄语”保留为产品名称，但内容每周更新，降低成本和上下文处理频率。
3. 日记“删除”限定为可恢复软删除，避免误触造成永久损失。
4. 新闻不保存正文；只保存公开摘要缓存，且不进入个人备份。
5. 设计稿必须覆盖恢复态、空态、错误降级和移动端，而非只覆盖理想首屏。

## 4. 主要风险与控制

- 外部新闻文本可能包含提示注入：作为不可信数据处理，模型 Prompt 固定，输出执行 Schema、长度和域名校验。
- Unsplash 使用须遵守热链和归因：只存展示元数据，失败使用内置渐变。
- Todo 状态和时间可能产生竞态：统一通过 revision-safe RPC 事务更新并追加事件。
- 日记恢复可能覆盖后续状态：软删除与恢复都要求 expected revision，冲突时重新读取。
- Vercel Runtime Cache 区域漂移可能导致缓存不一致：两个端点固定同一 Production 区域，并以最近成功版本降级。
- 当前 Production `/favicon.ico` 返回 404：属于非阻断静态资源缺口，在 2.5.0 页面重构阶段补齐。

## 5. 门禁

- Gate 2：PO 确认正式桌面/移动视觉稿、设计与技术方案后才开始生产功能代码。
- Owner Preview 写入、Supabase migration、自动化创建、PR 合并和 Production 发布分别需要当次明确确认，不复用此前授权。
- 验收仅使用公开合成 fixture 和专门创建的合成 Owner 记录，不操作真实日记。
