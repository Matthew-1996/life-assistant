# 发布准备 E1 · 预约业务备份

PO 在界面与批注修订完成后回复“好的，继续开发吧”，授权继续工程开发。本工作块仅完成预约业务备份链路（不超过 4 小时），不连接真实数据，不合并或部署。后续真实服务联调、数据库级灾难恢复、上线仍分别验收。

## 范围与裁决

- Ruling: 先做 E 中站内日历必需的业务备份，C/D Apple 订阅延后；主项无需等待外部日历，代价是本轮仍不能订阅。
- Ruling: v4 必须包含 fitness_appointments；旧 schema 2/3 继续生成 v3 归档且不添加空预约文件。缺少覆盖不能冒充零条预约，恢复不得用旧版缺失字段清空新表。
- 普通业务备份只增加预约（包括软删、revision、稳定 id），不包含 Owner 授权、幂等回执和订阅访问材料。后者必须使用受控数据库备份，不把业务 ZIP 当成完整灾难恢复。
- 保留 invoker、RLS、当前身份过滤；新增迁移不配置真实 Owner。

## 执行清单与证据

1. 已先观察 TS/Python v4 测试失败；SQL 导出仍为 schema 3 的断言失败。
2. 实现 SQL v4 投影、TS/Python 归档、安装器版本白名单与隔离校验兼容。

4. 运行全量检查并独立审阅，最终结果记录于 PMO。未执行真实备份、真实迁移或日历连接。

## 发布顺序与剩余门禁

先升级所有备份读取/安装组件至支持 v4，再应用 v4 导出迁移。旧安装器会拒绝 v4，不会安全地自动理解新格式；不得在旧代理还在运行时仅升级导出函数。

服务器实际 PostgREST 联调、私有数据库备份中新增表覆盖、隔离整库恢复后订阅撤销，以及真实迁移/Owner 配置仍为后续受控工作。本轮 ZIP 不能恢复幂等回执，因此不可用于对在线数据库的自动合并或替换；没有新增生产恢复入口。
