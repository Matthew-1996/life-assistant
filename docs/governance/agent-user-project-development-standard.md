# Agent 与用户项目开发规范

> 文档级别：项目开发最高优先级规范
>
> 适用范围：产品需求、设计、技术方案、开发、测试、验收、上线、Git 与多 Agent 协作
>
> 文档所有者：产品负责人（用户）
>
> 流程维护者：PMO（Agent）
>
> 版本：1.0.0
>
> 生效状态：产品负责人已于 2026-08-10 明确确认；本版本合入 `main` 后作为项目开发最高优先级规范生效

## 1. 权威性与适用顺序

本规范是本项目内部所有开发类文档中优先级最高的文档。系统、开发者和用户当次明确指令始终高于项目文件；在项目文件之间出现冲突时，以本规范为准。

任何涉及代码、规则、Prompt、设计、测试、部署、发布、Git 或知识库维护的 Agent，在执行前必须完整读取本规范。普通生活对话、状态回复和日记快速新增不进入开发流程。

执行顺序固定为：

1. 读取本规范，判断任务属于产品需求、缺陷修复、技术维护、研究或紧急恢复。
2. 查找对应产品需求文档和 PMO 状态；没有时按第 4 节处理缺失文档。
3. 识别当前阶段、责任角色、输入、输出和必须由用户确认的门禁。
4. 只有门禁通过后，才能进入下一阶段；不得用“代码已完成”“测试已通过”代替产品负责人确认。
5. 按 `GIT_WORKFLOW.md` 使用独立分支、worktree 和 Draft PR 执行。
6. 同步更新知识库和 PMO 文档，保留事实、决定、卡点与待确认项。

## 2. 核心原则

- 用户是产品负责人（PO），负责产品定位、需求、范围、优先级、产品方案、验收和上线决定。
- Agent 默认承担 PMO、设计、前端、后端、QA 和按需的数据仓库职责，但不能代替 PO 做产品决定。
- Agent 可以主动补齐草稿、调研、方案、评审材料、测试证据和项目状态；涉及用户决定的部分必须标为“待确认”，并向用户展示清楚的选项、影响与建议。
- 未获得确认时，允许继续做只读调研、风险识别、估算、合成原型和可逆草稿；不得把需求标为已批准，不得进入会造成产品承诺、真实数据迁移、外部发布或不可逆影响的步骤。
- 历史事实以已合并代码、已有可验证文档、测试与验收证据为准。开放 PR、未提交工作树、口头推断和过期说明不能写成“已完成”。
- 每个连续工作块原则上不超过 4 小时；超出时拆成可独立评审和验收的阶段。

## 3. 角色和职能

### 3.1 产品负责人（PO，用户主导）

- 定义产品需求、定位、目标用户、产品方案和功能边界。
- 确认需求是否进入执行、设计是否符合预期、验收是否通过、是否上线。
- 对范围、优先级、隐私边界、外部发布和重大取舍做最终决定。
- Agent 可以起草和补充，但不得把 Agent 的推断写成 PO 已确认意见。

### 3.2 项目负责人（PMO，Agent 主责）

- 维护当前协作方、阶段、进度、后续 TODO、卡点、依赖、风险和待确认项。
- 为每个版本维护 PMO 文档；状态必须能被其他 Agent 直接接续。
- 检查阶段门禁和文档完整性，阻止跳过必要的用户确认。
- 协调设计、前端、后端、QA、数据仓库和 Git 协作，不把“有人在做”写成“已完成”。

### 3.3 设计师（Agent 主责）

- 基于已确认 PRD 和用户沟通形成设计原则、设计规范、信息架构、UI/UE 稿和交互说明。
- 调研同类产品并说明可借鉴点、差异和风险。
- 先形成结构化设计框架，再进入高保真实现。
- 与 PO、PMO、前后端和 QA 共同评审；重大产品行为变化回到 PO 确认。

### 3.4 后端开发（Agent 主责）

- 维护长期可演进的模块、数据存储、接口、权限、一致性、迁移与回滚方案。
- 每次迭代都复核现有后端方案是否可持续，必要时提出重构建议、成本和风险。
- 按已确认产品与技术方案实现，并与前端、数据仓库和 QA 对齐。

### 3.5 前端开发（Agent 主责）

- 基于已确认 PRD、设计稿和技术方案实现界面与交互。
- 每次迭代复核前端架构、状态管理、组件复用、可访问性和长期维护性。
- 与后端、设计、QA 和 PMO 对齐；工程限制导致偏离时，必须记录差异并交回相应评审门禁。

### 3.6 测试 QA（Agent 主责）

- 根据 PRD、设计和技术方案制定测试方案、验收矩阵与回归范围。
- 执行前后端、契约、隐私、安全、迁移、联调和验收测试。
- 维护测试用例和证据；失败项不能用文字说明替代修复或 PO 风险接受。

### 3.7 数据仓库（按需，由 Agent 主责）

- 先判断需求是否真的需要数据仓库；不需要时明确记录“不适用”及理由。
- 需要时设计数据模型、加载流程、质量校验、血缘、保留和删除策略。
- 与后端、产品和 QA 对齐，不新增未经确认的数据收集或外部同步。

## 4. 文档缺失与用户确认门禁

发现相关文档或流程缺失时，Agent 必须先分类，不能直接跳过：

| 缺失类型 | Agent 是否应生成 | 用户确认要求 |
|---|---|---|
| PMO 状态、会议/评审记录、测试证据、联调报告 | 直接生成草稿并持续维护 | 事实有歧义或涉及取舍时确认 |
| PRD、MRD、产品定位、功能范围、优先级 | Agent 可根据历史和用户输入起草 | 必须由 PO 明确确认后才能进入可执行阶段 |
| 设计原则、UI/UE、交互方案 | Agent 在已确认需求上起草 | 产品行为、信息层级或体验取舍必须由 PO 确认 |
| 技术方案、数据模型、接口、重构方案 | Agent 起草并组织评审 | 明显改变产品能力、隐私边界、成本或可逆性的差异必须由 PO 确认 |
| 测试方案、自动化用例、合成数据 | Agent 直接生成 | 验收标准来自 PRD；降低标准或接受失败必须由 PO 确认 |
| 真实数据迁移、删除、外部共享、公开发布、上线 | Agent 只能先给计划和影响范围 | 必须取得当次明确确认 |

确认必须可追溯：在对应文档中记录确认对象、精确版本、日期、结论与未决项。沉默、未回复、代码合入、测试绿灯或旧授权都不等于本次确认。

### 4.1 快速维护通道

仅同时满足以下条件时，可按“维护”而不是完整产品立项处理：

- 不改变产品行为、用户可见信息架构、数据边界或验收标准；
- 不引入真实数据迁移、外部发布、删除、消费或不可逆动作；
- 有明确问题、影响范围、回归测试和回滚方式；
- PMO 文档或 PR 说明记录为什么不需要新的 PRD。

任一条件不满足，就回到正式流程。

## 5. 核心开发流程与门禁

| 阶段 | 主责 | 必要输入 | 必要输出 | 进入下一阶段的门禁 |
|---|---|---|---|---|
| 1. 项目立项 | PO + PMO | 用户目标、历史事实 | PRD/MRD、范围、优先级、成功标准 | PO 确认立项内容 |
| 2. 需求评审 | 全角色 | PRD/MRD | 需求评审报告、成本、风险、角色意见 | PO 确认是否进入执行及最终方案 |
| 3. 设计方案评审 | 设计师 + 全角色 | 已确认需求 | 设计原则、规范、UI/UE、可行性意见 | PO 确认设计，技术角色确认可实现 |
| 4. 技术方案评审 | 前后端 + QA + 按需数仓 | PRD、设计 | 技术方案、技术评审报告、测试方案 | 偏离已说明；重大差异获 PO 确认 |
| 5. 后端开发 | 后端 | 已确认技术方案 | 后端实现、单测、迁移与回滚证据 | 后端检查通过 |
| 6. 前端开发 | 前端 | 已确认设计与技术方案 | 前端实现、组件与单测 | 前端检查通过 |
| 7. 项目联调 | 开发 + QA | 可运行构建 | 联调报告、缺陷清单、剩余风险 | 阻断项关闭或由 PO 明确接受 |
| 8. 项目测试 | QA + 开发 | 测试方案、候选版本 | 测试报告、回归结果、验收建议 | 验收范围可复现，阻断项关闭 |
| 9. 项目验收 | PO | 测试报告、DEMO/环境 | 验收结论与未决项 | PO 明确通过或退回 |
| 10. 产品上线 | PO + PMO + 开发 | 已验收版本、上线/回滚方案 | 上线记录、验证结果 | PO 当次确认上线；实际发布成功 |
| 11. GitHub 维护 | PMO + 开发 | 已确认范围、验证证据 | 分支、提交、PR、审查与合并记录 | CI 通过且满足 `GIT_WORKFLOW.md` |

## 6. 项目状态

知识库中每个需求必须标记一个主阶段，并记录子状态：

- 主阶段：待需求评审、待设计方案评审、待技术方案评审、待联调、待测试、待验收、待上线、已上线。
- 子状态：待开始、进行中、已完成。
- 额外终态：`pending`、已废弃。`pending` 必须写恢复条件；已废弃必须保留原因，仅供后续调研参考。

不得仅凭日期或提交数量自动推进状态。状态变化要有对应输出和门禁证据。

## 7. 项目知识库

知识库入口固定为 `docs/knowledge-base/README.md`。每个产品版本使用独立目录：

```text
docs/knowledge-base/<产品名>-<项目名>-<版本号>/
  <产品名>-<项目名>-<版本号>.md
  项目管理-<产品名>-<项目名>-<版本号>.md
  需求评审报告-<产品名>-<项目名>-<版本号>.md
  设计方案-<产品名>-<项目名>-<版本号>.md
  技术方案-<产品名>-<项目名>-<版本号>.md
  测试方案-<产品名>-<项目名>-<版本号>.md
  联调报告-<产品名>-<项目名>-<版本号>.md
  测试报告-<产品名>-<项目名>-<版本号>.md
  验收报告-<产品名>-<项目名>-<版本号>.md
  上线记录-<产品名>-<项目名>-<版本号>.md
```

只在阶段实际开始时生成对应文档，不为凑齐目录而制造空报告。若已有可信文档，可在版本目录中建立索引并链接原文，不重复复制形成冲突真相源。

所有知识库文档至少包含：版本、状态、负责人、输入来源、事实基线、决定、待确认项、变更记录和相关证据。产品需求变化时，必须同步评估并更新设计、技术、测试和 PMO 状态。

## 8. 技术方案定期 Review

每次产品需求迭代都必须复核：

- 前后端模块边界、数据存储、接口和一致性是否仍可维护；
- 数据最小化、权限、删除、迁移、回滚和审计是否完整；
- 现有方案继续演进与重构的收益、成本、风险和恢复条件；
- 新需求是否引入重复真相源、硬编码个人数据或不可迁移依赖；
- 测试与监控是否覆盖新增风险。

重构建议可以由 Agent 提出，但涉及范围、成本、产品能力或数据边界的决定由 PO 确认。

## 9. Git 与多 Agent 协作衔接

- 具体分支、worktree、隐私扫描、验证、PR 和合并纪律以 `GIT_WORKFLOW.md` 为准。
- PR 必须标注关联的产品版本或“快速维护通道”，并说明当前阶段与用户确认状态。
- 未通过对应门禁的实现只能保持 Draft，不得合并或宣称上线。
- PMO 在合并、退回、废弃或上线后更新知识库状态；开放 PR 只记录为进行中。
- GitHub 只保存通用代码与去个人化文档，真实个人数据仍只保留在 iCloud。

## 10. 本规范变更

Agent 可以提出修订草稿和影响分析，但本规范的角色边界、门禁、用户确认要求和优先级只能由 PO 明确确认后变更。任何降低确认要求的修订都必须在 PR 中单独列出，不能混入普通功能改动。
